## 5. Shadow validation (non-breaking proof)
`shadow_compare(assembled_regimens, normalized_regimens)`: **compared 2,675, matches 2,675, diffs 0,
divergence_rate 0.0000.** The assembly layer reproduces the engine-relevant backbone fields (drug,
dose, duration) exactly and adds enrichment purely additively — it does not alter what the Clinical
Engine would receive. This is the evidence that a future cutover is non-breaking.

## 6. Honest findings (registered, not fixed — STRICT RULE #6)
- **RC-023** (from Phase 0 audit): kb_p44 atomic objects have no intra-regimen linkage — the reason
  assembly sources structure from `normalized_regimens`, not atomic facts. Open.
- **RC-024** (from this run): 42% REJECT rate at Gate 1, driven by 754/2,675 (28.2%) source rows with
  NULL numeric dose (scheme-based doses). The layer correctly fails-closed; whether null-numeric dose
  should be REVIEW (physician quantifies) vs REJECT is a governance/clinical decision — registered,
  Gate 1 NOT changed unilaterally. Open.

## 7. Determinism & provenance
- Assembly is a pure function of (normalized_regimens snapshot, kb_p44 snapshot, ruleset
  `p5.3-v1`) — sorts fully keyed, no wall-clock in content, re-runnable identically.
- Every regimen field carries `FieldProvenance` (`source_object_id`, `source_document`,
  `source_location`, `source_store`, `scope`). Enrichment fields are tagged `scope="guideline"`
  (guideline-scoped, honestly labeled, not claimed regimen-specific).
- Conflicts are stored as `ConflictRecord`s with `resolution_status=UNRESOLVED` — routed to review,
  never auto-picked.

## 8. Can we proceed to P6 (Clinical Decision Engine)?
**Partially — with one explicit gate.** The assembly layer is implemented, tested, deterministic,
provenance-complete, and shadow-proven non-breaking. However:
- P6 (making the engine *consume* assembled regimens) should NOT begin until the review/approval
  workflow has produced a body of `PHYSICIAN_APPROVED`/`PUBLISHED` regimens — currently everything is
  `REVIEW_REQUIRED` (by design: no automated approval). The engine must only serve approved regimens
  (P5.2 governance), so P6's precondition is a populated approval pipeline, which requires physician
  capacity (`CLINICAL_VALIDATION_FRAMEWORK.md`), not more engineering.
- RC-024 (reject rate) should get a governance decision first, or ~42% of the corpus is unavailable
  to the engine.
- The engine switch itself remains gated behind the full `MIGRATION_PLAN_NORMALIZED_REGIMENS.md`
  shadow→parity→cutover sequence; this report delivers the assembly + shadow-compare foundation for
  that, not the cutover.

**Recommendation:** P5.3 assembly layer is production-grade and ready. Before P6, resolve RC-024
(governance) and run the review/approval workflow to build an approved-regimen corpus. The
engineering path to P6 is unblocked; the clinical-governance path is the gating dependency.

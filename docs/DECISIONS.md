# DECISIONS — Architecture Decisions

> Архитектурные решения проекта ANTIBIO (pipeline + calculator)

---

## Decision 1: Единый проект ANTIBIO

**Дата:** 2026-07-08
**Решение:** Объединить clinrec_downloader (pipeline) и antibio-calc (HTML-калькулятор) в единый проект ANTIBIO.
**Почему:** Оба проекта работают с одной предметной областью — КР МЗ РФ по антибиотикам. Разделение приводит к дублированию документации и контекста.
**Последствия:** Код pipeline переносится в `src/pipeline/`, данные в `db/`, документация в `docs/`. HTML-калькулятор остаётся в корне.

---

## Decision 2: Документация в docs/

**Дата:** 2026-07-08
**Решение:** Вся документация pipeline хранится в `docs/`. Корневые файлы (AGENTS.md и др.) — legacy для HTML-калькулятора.
**Почему:** Чёткое разделение контекстов. Новый агент читает `docs/` для pipeline, корень — для calculator.
**Последствия:** 6 файлов в `docs/`, 5 файлов в корне.

---

## Decision 3: Перенос без изменений

**Дата:** 2026-07-08
**Решение:** Код из clinrec_downloader переносится в ANTIBIO/src/pipeline/ без изменений (материальный перенос файлов).
**Почему:** Код стабилен, 39 тестов проходят. Рефакторинг после интеграции.
**Последствия:** Импорты могут потребовать корректировки (изменение относительных путей).

---

## Decision 4: Python 3.12 полный путь

**Дата:** 2026-07-08
**Решение:** Использовать полный путь: `$env:LOCALAPPDATA\Programs\Python\Python312\python.exe`
**Почему:** Python 3.12 не в PATH. Установка user-local.
**Последствия:** Все команды через переменную `$py`.

---

## Decision 5: SQLite + JSON двойное хранение

**Дата:** 2026-07-08
**Решение:** Метаданные в SQLite (`metadata.sqlite`) + JSON (`clinrecs.json`, `antibiotic_guidelines.json`)
**Почему:** SQLite — для запросов. JSON — для отладки.
**Последствия:** Синхронизация при обновлении. Избыточность приемлема (< 10 MB).

---

## Decision 6: A/B/C/D классификация перед LLM

**Дата:** 2026-07-08
**Решение:** Rule-based классификация ДО LLM извлечения
**Почему:** Level C (только упоминания) и D (нет антибиотиков) не требуют LLM — экономия ~40% токенов
**Последствия:** Level C → review_required.json без LLM

---

## Decision 7: DeepSeek V4 Pro + GLM 5.2

**Дата:** 2026-07-08
**Решение:** Разделить извлечение и валидацию на разные LLM
**Почему:** Две разные модели = двойная проверка, снижение галлюцинаций
**Последствия:** Каждый PDF требует 2 API-вызова

---

## Decision 8: Source traceability

**Дата:** 2026-07-08
**Решение:** Каждая схема содержит 6 source-полей (guideline_name, code_version, pdf_file, page_number, section_name, source_quote)
**Почему:** Медицинские данные требуют проверяемости
**Последствия:** Без любого поля → review_required.json

---

## Decision 9: Per-field confidence scores

**Дата:** 2026-07-08
**Решение:** Каждое поле имеет confidence 0.0-1.0 (dose, unit, frequency, route, duration, age_group, renal, pregnancy)
**Почему:** Разные поля извлекаются с разной уверенностью
**Последствия:** Порог < 0.8 → review_required.json

---

## Decision 10: Section detection перед LLM

**Дата:** 2026-07-08
**Решение:** Перед LLM извлекать только релевантные страницы
**Почему:** PDF 50-200 стр, лечение на 5-15 стр. Экономия 80-90% токенов
**Последствия:** LLM получает только relevant_text

---

## Decision 11: Incremental reprocessing по SHA256

**Дата:** 2026-07-08
**Решение:** SHA256 PDF → повторно обрабатывать только изменившиеся
**Почему:** КР обновляются. Не нужно переобрабатывать всё.
**Последствия:** extraction_progress.json хранит SHA256 + статус

---

## Decision 12: Strict separation raw / validated

**Дата:** 2026-07-08
**Решение:** Unvalidated LLM output НИКОГДА не в SQLite/knowledge_base.json
**Почему:** Медицинские данные требуют верификации
**Последствия:** raw → validated → review — три стадии

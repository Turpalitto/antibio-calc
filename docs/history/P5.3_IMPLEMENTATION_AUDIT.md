## 1. What exists (verified read-only against the real repo, 2026-07-15)

### 1.1 kb_p44 read API
`src/pipeline/knowledge_base.py`:
- `get_active(type_=None) -> List[Dict]` — returns objects with `status='active'`, content JSON
  parsed. **This is the only structured read method** (besides `_get_by_key` substring-dedup and
  `get_reviews`). No query-by-guideline, no query-by-page, no relational join API.
- `objects` table columns: `id, type, content, version, status, created_at, confidence, history,
  knowledge_type, clinical_domain, updated_at, validation_status, review_status,
  normalization_status, relationships`.
- `provenance` table (certified 2026-07-15): `obj_id, pdf, guideline_id, page, table_row, table_col,
  table_conf, original_text, normalized_value, layout_engine, semantic_engine, schema_version, ...`.

### 1.2 Object content shapes (real samples)
- `Medication`: `{raw, normalized, confidence, provenance, normalization_status, name}`
- `Dose`: `{..., value, unit, subtype}`
- `Contraindication`: `{..., condition, subtype}`
- `Evidence`: `{..., level, subtype}`
- `Diagnosis`: `{..., name}`
- Real counts: Medication 2,788 · Dose 24,705 · Contraindication 841 · Evidence 2,190 ·
  Diagnosis 431 · Recommendation 381.

### 1.3 The regimen-grained store (LLM pipeline)
`metadata.sqlite::antibiotic_regimens` — 2,675 rows, 100% `validated=1`, each row = ONE complete
regimen with `antibiotic, dose, unit, route, frequency, duration, age_group, pregnancy,

associated (the LLM extracted them together as a unit). `normalized_regimens.sqlite` is its
normalized projection (also 2,675). This is what the Clinical Engine reads today.

## 3. What is MISSING — the foundational finding (CRITICAL)

**kb_p44 atomic Knowledge Objects have NO intra-regimen linkage. They cannot be deterministically
assembled into clinically-correct regimens as P5.3 Phases 2–3 literally specify.**

Evidence (direct, read-only):
- **`relationships` column is empty on 100% of objects** (0 rows with non-empty relationships). No
  object references any other object.
- Objects cluster only by `(guideline_id, page)`. Example (guideline 2043): page 16 holds 54 objects
  (2 Medication + ~52 Dose); page 15 holds 31 Doses. **There is no data saying which of the 52 doses
  belongs to which of the 2 drugs.** The associations a regimen needs (drug↔dose↔route↔frequency↔
  duration) were never captured during extraction.
- Object quality is noisy at the atomic level (observed `Dose` with `raw=","`, `normalized="|"`,
  `page=0`; a `Dose` carrying `subtype="route"`). The atomic layer optimized for provenance coverage,
  not relational fidelity — consistent with the **measured `CKY.overall=10.3%` and `CKY.tables=1.1%`**
  from the P4.4 certification (`pr008_yield_FINAL.json`).

**Why this is a safety blocker, not a quality nuance:** the P5.3 success criterion is "каждый regimen
должен быть объясним до конкретной строки клинической рекомендации." A regimen assembled by combining
2 drugs × 52 unlinked doses on one page cannot answer "which dose goes with which drug" — it would be
a combinatorial guess. Publishing such a regimen would violate the core explainability guarantee. A
deterministic engine over non-relational input produces deterministically-wrong pairings, which is
worse than no output.

Registered as **RC-023** (`ROOT_CAUSE_REGISTER.md`), not fixed here.

## 4. The safe path already exists in prior design
P5.1's `MIGRATION_PLAN_NORMALIZED_REGIMENS.md` §2 already anticipated this and chose the pragmatic
v1 source: **assemble `ClinicalRegimen` from the regimen-grained `antibiotic_regimens` rows** (which
carry correct intra-regimen associations + source_pdf/page/source_quote for line-level
explainability), **enriched** with kb_p44 `Evidence`/`Contraindication` objects linked by
`guideline_id` (net-new clinical value kb_p44 uniquely has — Evidence 2,190, Contraindication 841).
This audit provides the direct evidence that confirms that decision was correct: the atomic-only
assembly path is not viable for v1.

**This does NOT abandon kb_p44 as the SSOT** (P5.0 `SINGLE_SOURCE_OF_TRUTH_RFC.md`). It means the
`ClinicalRegimen` canonical objects are populated in v1 primarily from the regimen-grained source +
kb_p44 enrichment, and the atomic-fact-only assembly path becomes viable later once intra-regimen
linkage exists (RC-023 fix — an extraction-layer enhancement, out of P5.3 scope).

## 6. Decision required before code (this is a genuine fork, per STRICT MODE)

The mandate's Phases 2–3 say "Input: Knowledge Objects → assemble." §3 proves that input cannot
produce explainable regimens in v1. Two honest options:

- **Option A — Implement literally as written** (assemble from kb_p44 atomic objects). **Not
  recommended.** Produces non-explainable, combinatorially-guessed drug↔dose pairings; violates the
  success criterion; would generate regimens that fail the very safety/provenance gates P5.2 defines.

- **Option B — Implement with the P5.1-sanctioned v1 source** (assemble from regimen-grained
  `antibiotic_regimens`, enrich from kb_p44 Evidence/Contraindication, full provenance to the
  source_quote line). **Recommended.** Every regimen is explainable to a specific clinical-recommendation
  line (the `source_quote`), satisfies the success criterion, reuses certified provenance discipline,
  and matches the migration plan already designed and accepted in P5.1. The atomic-fact assembly path
  is deferred until RC-023 (intra-regimen linkage) is resolved at the extraction layer.

**Recommendation: Option B.** It is the only option that satisfies "каждый regimen объясним до
конкретной строки" with today's data. Proceeding requires owner confirmation of the scope shift from
"assemble from atomic Knowledge Objects" to "assemble from regimen-grained source + Knowledge Object
enrichment," because it deviates from the literal Phase-2 wording — exactly the kind of
requirement/repository contradiction that STRICT MODE + the project constitution say to surface
before acting, not paper over.

## 7. Audit conclusion
- **What exists:** a certified atomic-fact KB (kb_p44), a regimen-grained validated store
  (antibiotic_regimens), an engine port to implement against (`RegimenProvider`), reusable
  normalization + provenance + versioning machinery.
- **What's reusable:** all of the above — P5.3 is additive, nothing rebuilt.
- **What's missing:** intra-regimen linkage in kb_p44 (RC-023) — the blocker for literal atomic
  assembly.
- **Files to change:** listed in §5 (Option B), all additive, engine untouched.
- **No code written.** Awaiting the §6 scope decision, per Phase 0's "no code until audit complete"
  and the anti-rush mandate.

## 2. Принципы (неизменяемые)

1. **Evidence-first.** Каждая находка содержит `путь:строка` и/или воспроизводимую
   команду с фактическим выводом. Без доказательства — не находка, а гипотеза
   (помечается отдельно в §«Не удалось верифицировать»).
2. **Repository > docs > chat.** Если документ утверждает X, а код/тест показывает Y —
   истиной считается Y, расхождение фиксируется как находка.
3. **Clinical safety first.** Приоритет областей: (a) риск неверной дозы/схемы для
   пациента → (b) утечка PHI/секретов → (c) ложный «зелёный» статус (тесты/CI/доки,
   которые скрывают дефект) → (d) сопровождаемость → (e) всё остальное.
4. **Не доверять предыдущему аудиту.** Все «закрытые» находки `AUDIT_2026-10-05.md`
   перепроверяются на HEAD как новые.
5. **Измерять, а не оценивать.** Числа (тесты, записи БД, размеры, покрытие) берутся
   из реального прогона на этой машине с указанием команды.
6. **Не раздувать.** Дубли схлопываются; стилистика без влияния на (a)–(d) не
   входит в отчёт, максимум — одна строка в «LOW/замечания».
7. **Каждая находка = действие.** Формат: Что / Где / Почему важно / Как исправить /
   Как проверить, что исправлено.

## 3. Область аудита и чек-листы

### A. Воспроизводимость и среда
- [ ] Python/Node версии; наличие `.venv`; `uv sync --frozen` из `uv.lock`; что реально
      установлено vs что требует `pyproject.toml`.
- [ ] `npm run validate`, `npm run build`, `npm test`, `pytest -q` (testpaths) — реальный
      прогон, фактические числа passed/failed/skipped/xfail, время.
- [ ] Тесты вне `testpaths` (`tests/`, `dose_verification_sandbox/`, `generated/`) —
      собираются ли, сколько skip по отсутствующим артефактам.
- [ ] Воспроизводимость артефакта `antibiotic_calc.html` (template + db → byte-identical?).
- [ ] CI `.github/workflows/ci.yml`: соответствует ли локальному прогону; слепые зоны.

### B. Клиническая безопасность данных и расчётов (главный блок)
- [ ] Схема БД `db/` (index.json, diseases/*.json, schema.json): целостность ссылок
      drug↔regimen↔scenario↔disease, обязательные поля, единицы.
- [ ] Логика расчёта дозы в `antibiotic_calc.html.template`: mg/kg/day vs mg/kg/dose,
      деление на кратность, max-дозы (per dose / per day), округление, детские формы,
      концентрация суспензий (мг/мл → мл), ЕД vs мг, Infinity/NaN/0 пути.
- [ ] Граничные значения ввода: вес 0/отрицательный/>300 кг, возраст, СКФ, беременность.
- [ ] Записи с `calculation_blocked` — реально ли блокируются в UI и в сборке.
- [ ] Источники: есть ли у каждой схемы ссылка на КР (id/страница), статус верификации.
- [ ] Clinical Engine: fail-closed инварианты, UNKNOWN≠MODERATE, exclusion-with-reason,
      трассировка (7 вопросов Traceability Rule) в v1 и v2.
- [ ] Golden cases: есть ли, запускаются ли, что покрывают.
- [ ] Скрипты сборки БД (`db/build_db.py`, `calculator_source_gate.py`): дефолты,

### C. Безопасность приложения (AppSec)
- [ ] `server.js`: traversal, allowlist, прокси (SSRF/open relay), hop-by-hop, CSP,
      заголовки, методы, DoS (размер тела, таймауты).

## 4. Шкала серьёзности

| Уровень | Критерий |
|---|---|
| **CRITICAL** | Может привести к неверной дозе/схеме у пациента, утечке PHI/секретов, или скрывает такой дефект (ложно-зелёный гейт). |
| **HIGH** | Нарушение собственных законов проекта (fail-closed, traceability), дыра в security-контроле, невоспроизводимая сборка/релиз. |
| **MEDIUM** | Снижает надёжность/сопровождаемость; противоречивая «память проекта»; слепые зоны тестов. |
| **LOW** | Гигиена, стиль, мелкие несоответствия без прямого риска. |
| **INFO** | Наблюдение/рекомендация «добавить». |

## 5. Формат итогового отчёта (`AUDIT_2026-10-14.md`)

0. Шапка: HEAD, дата, среда (python/node/uv), команды верификации.
1. Executive summary (≤10 строк): общий вердикт, топ-5 рисков.
2. Статус находок прошлого аудита (таблица: ID → заявлено → факт на HEAD → вердикт).
3. Находки по серьёзности (CRITICAL → LOW), каждая в формате §2.7, с ID
   `A-xx` (среда), `B-xx` (клиника), `C-xx` (security), `D-xx` (код), `E-xx` (тесты),
   `F-xx` (доки), `G-xx` (гигиена), `H-xx` (PWA).
4. Проверено и чисто (что явно проверено и дефектов нет — чтобы не перепроверять).
5. Не удалось верифицировать (и почему).
6. План действий: три списка — **Исправить** (bugs), **Улучшить** (existing), **Добавить**
   (missing) — с приоритетом и оценкой трудоёмкости (S/M/L).
7. Приложение: сырые метрики (тесты, LOC, размеры, ruff-сводка).

## 6. Порядок выполнения

1. Инвентаризация (структура, размеры, языки, точки входа).
2. Среда: установить зависимости из lock, прогнать все гейты, зафиксировать числа.
3. Блок B (клиника) — глубже всего: чтение JS-расчёта построчно, проверка БД скриптом.
4. Блок C (security) — server.js, api, template, grep секретов/PII.
5. Блоки D/E — линтеры, тесты, мёртвый код.
6. Блоки F/G/H — доки, гигиена, PWA.
7. Перепроверка прошлого аудита.
8. Сборка отчёта; самопроверка: у каждой находки есть evidence и действие.

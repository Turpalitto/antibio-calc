# RCA — Качество медицинской базы ANTIBIO (design-level документ)

> **Назначение:** основа дорожной карты по качеству данных. НЕ отчёт об анализе, а технический design-документ.
> **Статус:** read-only анализ. Код, Medical Normalizer, Medical Dictionary, diagnosis_index, knowledge_base, SQLite, PDF, любые медицинские данные — **НЕ изменялись**.
> **Источники:** `clinical_data_issues.json` (4506 записей, `pending_review`) + read-only запросы raw `antibiotic_regimens` ↔ `normalized_regimens`. PDF-подтверждено только guideline 1638.
> Все прогнозные числа — **оценки / верхние границы**, не обещания.

---

## ★ ГЛАВНЫЙ ВЫВОД (цитировать при любом планировании)

> ## Нормализатор близок к своему архитектурному потолку.
>
> Сумма всех verdict-улучшений **без переэкстракции** ≈ **до ~438 (REVIEW→PASS) + до ~80 (REJECT→better)**; пол REJECT ≈ **~1113**. Дальнейшая работа над парсером/словарём даёт **проценты, а не порядок величины**.
>
> **Следующий скачок качества на порядок возможен ТОЛЬКО через улучшение extraction** — потому что **~961 REJECT (81% всех REJECT)** обусловлены отсутствием данных уже в raw extraction, и парсер там бессилен по определению.

Это архитектурное ограничение важнее любых процентов. Именно его следует держать в голове при приоритизации.

---

## Закон проекта (attribution law)

> **Если поле присутствует в raw extraction → это проблема parser / normalizer** (чинится re-normalization, без переэкстракции).
>
> **Если поля нет в raw extraction → это ИСКЛЮЧИТЕЛЬНО проблема extraction** (re-normalization бессилен, нужна реконструкция).

Эта формулировка снимает большинство бессмысленных обсуждений «чинить парсер или переизвлекать»: ответ детерминирован присутствием поля в raw.

---

## Архитектурная схема потоков ошибок

```
                         PDF (КР Минздрава)
                          │
                          ▼
                  LLM extraction  ◄── ПЕРВОПРИЧИНА большинства REJECT
                          │            (промпт извлекает ТЕКСТ,
                          │             а не реконструирует ТАБЛИЦУ)
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
       raw COMPLETE               raw INCOMPLETE
   (поле есть в сыром)         (поля нет в сыром)
             │                         │
             ▼                         ▼
        Normalizer            STRUCTURED THERAPEUTIC
   (parser/dictionary/          TABLE RECONSTRUCTION
    preprocessing)             (executor-agnostic: любой LLM
             │                  или собственный pipeline)
             ▼                         │
        Clinical DB  ◄─────────────────┘
      (PASS/REVIEW/REJECT)
```

Левая ветвь = дёшево, чинится кодом нормализатора. Правая ветвь = дорого, требует реконструкции терапевтической таблицы.

---

## ★ Ключевой инсайт (уровень выше regex)

> **Промпт extraction ориентирован на извлечение ТЕКСТА, а не на реконструкцию терапевтической ТАБЛИЦЫ.**

Поэтому из многорядной «Таблицы 1» (первая линия + альтернативы + при аллергии) стабильно берётся один ряд: guideline 1638 — 1 из 14 схем; guideline 1220 — 1 из 12. Бесконечное улучшение regex здесь не поможет — проблема на уровень выше.

**Терминология (важно):** задачу правой ветви называем **Structured Therapeutic Table Reconstruction (STTR)** — по функции, а не по технологии. Исполнитель (Claude / GPT / Gemini / Qwen / собственный pipeline) может смениться; архитектурная задача — нет.

### DRUG_UNKNOWN — реальная декомпозиция (438 REVIEW, 153 уникальные строки)

Порядок работ — **Preprocessing → Tokenizer → Dictionary → Morphology** (а не «сначала словарь»):

| Под-причина | Кол-во | Действие | Пример |
|---|---:|---|---|
| **1. Preprocessing** (маркеры `**`/`®`/`#`, скобки, падеж) | **~331** | очистка ДО lookup | `амоксициллином**` (амоксициллин, известен!) |
| **2. Combination/Tokenizer** | ~11 | разбор комбинаций | `бетаметазон+гентамицин+клотримазол` |
| **3. Dictionary** (реально нет) | **~91** | +запись | `пефлоксацин`, `миноциклин` |
| **4. Morphology** | ~5 | лемматизация | `рифаксимина`, `норфлоксацина` |

**Вывод:** «расширить словарь» закрывает лишь ~91. Доминирует **preprocessing (~331)** — очистка маркеров/падежей, не новые записи.

## ⛔ Отдельный блок — DAILY-DOSE: НЕ АВТОИСПРАВЛЯТЬ

`4,5 г **каждые 6 часов**` (=×4, корректно) и `1,5 г/**сут**` (суточная) для regex почти неотличимы. Массовый авто-фикс сам по себе опасен.
**Правило:** исправлять только по **whitelist проверенных паттернов** + **обязательная врачебная сверка каждой** затронутой схемы. verdict не меняется — это коррекция значения дозы. 1638 подтверждён; остальные ≤61 — только после ручной верификации.

## Стратегический план (фазы)

- **Фаза A — дёшево, без STTR, без PDF (max ROI):** Preprocessing/Tokenizer + Dictionary (DRUG_UNKNOWN) + Duration + Dose/Freq парсеры → одна re-normalization.
  Прогноз (**оценка, не обещание**): Estimated PASS ≈ upper bound **~1500**, Estimated REVIEW ≈ **35–50**, REJECT floor ≈ **~1113**.
- **Фаза B — SAFETY:** whitelist daily-dose + врачебная сверка ≤61 (с 1638).
- **Фаза C — STTR (отдельный проект):** реконструкция таблиц для 961 полей + 83 guideline. **Единственный путь** к REJECT <25% и восстановлению альтернативных схем (важно для аллергиков). Executor-agnostic.
- **Фаза D — курация:** dedup diagnosis_index (182 gid).

## Что отвечает этот RCA (4 вопроса технического RCA)
1. **Что сломано?** → категории issue_code (реестр).
2. **Почему?** → закон атрибуции + архитектурный инсайт про таблицы.
3. **Чинится ли текущим пайплайном?** → левая ветвь (re-norm) да; правая (STTR) нет.
4. **Где предел архитектуры?** → нормализатор у потолка; порог REJECT ≈ 1113 без STTR.

# PERSONAL_PHYSICIAN_MODE_RFC.md

## RFC — Local Personal Physician Decision-Support Mode

**Status:** DRAFT — design only; no implementation or governance activation
**Date:** 2026-08-01
**Owner request:** preserve the application as designed while enabling a real,
local physician-owner workflow
**Requires explicit acceptance before implementation:** yes
**Touches frozen contracts:** yes; all changes must be additive and versioned

## 1. Decision sought

Add an explicit, local-only `PERSONAL_PHYSICIAN` operating mode that may show
source-traced antibiotic decision support to the physician-owner from a
separately curated owner-reviewed dataset.

This mode must not:

- change the existing calculator's default behaviour;
- relabel single-physician review as `PHYSICIAN_APPROVED`;
- weaken Production Guard for production/public modes;
- read unreviewed extraction output as clinical recommendations;
- silently select a dose, formulation, route, or regimen;
- publish patient data or expose the local API beyond loopback;
- connect Review Workbench state directly to the frozen Engine kernel.

## 2. Why a separate mode is required

The current system has two distinct realities:

1. `antibiotic_calc.html` is an offline-first calculator with embedded data and
   deterministic client-side dose/formulation calculations.
2. Clinical Engine API v1 is fail-closed. Its real endpoint currently returns
   only recommendation identifiers, and without an approved recommender it
   returns `REVIEW_REQUIRED / KNOWLEDGE_UNAVAILABLE`.

Reusing `research`, `development`, or `strict_mode=False` would be unsafe:
those profiles allow uncurated data for engineering analysis and do not define
a physician-facing evidence contract. `PERSONAL_PHYSICIAN` therefore needs its
own guard and data status.

## 3. Non-negotiable compatibility contract

### 3.1 Default application remains unchanged

Opening `antibiotic_calc.html` normally must preserve byte-for-byte observable
behaviour of the accepted calculator workflow:

- disease and scenario selection;
- adult/child branching;
- weight-based and fixed-dose arithmetic;
- daily-dose versus per-administration semantics;
- maximum-dose caps;
- frequency and duration display;
- dosage-form and suspension calculations;
- amoxicillin/clavulanate alternatives and existing formulation logic;
- source links, warnings, prescription rendering, printing, and offline use.

Existing calculation functions remain the sole calculation implementation.
Personal mode may supply a selected, validated regimen DTO to those functions;
it must not duplicate or reimplement their arithmetic.

### 3.2 Explicit opt-in only

Personal mode is never inferred. Activation requires all of:

- loopback origin (`127.0.0.1` or `localhost`);
- explicit application setting `PERSONAL_PHYSICIAN`;
- a locally registered physician-owner identity;
- a matching local mode token/session generated by the local service;
- an accepted owner-reviewed snapshot version;
- visible acknowledgement that this is single-physician decision support, not
  independently validated production content.

If any condition fails, the application remains in its existing standalone
calculator mode or returns `REVIEW_REQUIRED`; it never falls through to
unreviewed Engine output.

## 4. Governance vocabulary

Add a status that is deliberately distinct from production approval:

`OWNER_REVIEWED_EXPERIMENTAL`

Meaning:

- one identified physician-owner reviewed the exact source-linked object;
- source fidelity and required structural checks passed;
- the object is eligible only for local `PERSONAL_PHYSICIAN` mode;
- independent Reviewer B and Medical QA have not approved it;
- it cannot transition automatically to `PHYSICIAN_APPROVED` or `PUBLISHED`;
- it is excluded from production bundles and production metrics.

The status is not added to the existing production approval state machine by
reinterpretation. It belongs to a separate personal-mode attestation ledger.
Production lifecycle states remain unchanged.

## 5. Data boundary

Personal mode consumes a separate immutable bundle, for example:

`personal_physician_bundle_v1`

Each eligible regimen must contain:

- stable regimen and guideline identifiers;
- exact guideline title, rubricator identifier/version, approval year, and
  source URL;
- source PDF hash, page, and exact source wording;
- drug/combination identity and formulation basis;
- dose value/range, dose basis, route, frequency, duration, and maximum dose;
- population limits and all available renal, hepatic, pregnancy, lactation,
  pediatric, neonatal, allergy, interaction, and contraindication data;
- complete terminology mappings that affected the result;
- owner identity, attestation timestamp, rationale, and source snapshot hash;
- build version and deterministic content hash.

Missing required clinical fields never receive defaults. Such an object stays
`REVIEW_REQUIRED` and is not recommendation-eligible.

The bundle is generated from reviewed canonical objects. It must never read
directly from PDFs, raw extraction JSON, the C7 source-fidelity event file, or
the production Review Workbench database at Engine runtime.

## 6. Personal-mode guard

Introduce an additive guard outside the frozen ten-stage Engine kernel:

`PersonalPhysicianGuard`

It validates before a recommender is constructed:

1. operating mode is explicitly `PERSONAL_PHYSICIAN`;
2. server is loopback-only;
3. physician-owner registration is active;
4. bundle status is `OWNER_REVIEWED_EXPERIMENTAL`;
5. bundle schema/version/hash/signature are valid;
6. every served regimen has complete provenance and attestation;
7. no production approval claim is present;
8. request-audit storage is local and append-only;
9. patient information is not persisted unless explicitly enabled locally;
10. current guideline-version status is displayed and stale/unknown status is
    fail-closed.

Production Guard remains unchanged. `Profiles.production()` remains strict.
`Profiles.research()` and `Profiles.development()` cannot activate personal
mode.

## 7. API contract

API v1 remains unchanged for backward compatibility.

Personal mode requires API v2 because the application needs complete
physician-visible recommendation data, not the identifier-only v1 envelope.

Proposed request addition:

```json
{
  "api_version": "2",
  "operating_mode": "PERSONAL_PHYSICIAN",
  "query": {
    "diagnosis": "...",
    "icd10": "...",
    "patient": {
      "age": 0,
      "weight_kg": 0,
      "pregnant": false,
      "renal_function": "...",
      "hepatic_impairment": false,
      "allergies": [],
      "current_meds": []
    }
  }
}
```

Proposed successful status:

`OWNER_REVIEWED`

It must never be serialized as `APPROVED`.

Each recommendation includes:

- regimen/guideline IDs and therapy line;
- drug or combination and component basis;
- dose/range/basis, route, frequency, duration, and maximum-dose constraints;
- population and safety conditions;
- alternatives considered and rejection reasons;
- source references and exact wording;
- terminology mappings and participating Engine stages;
- deterministic calculation inputs/output and rounding steps;
- `governance_status: OWNER_REVIEWED_EXPERIMENTAL`;
- a non-dismissible local-mode banner payload.

Failure remains explicit: `REVIEW_REQUIRED`, `BLOCKED`, or `ERROR`, always with
an empty recommendation array when the guard or evidence contract fails.

## 8. Application integration

The existing site remains an offline calculator first.

Personal-mode integration is additive:

1. User opens the ordinary calculator; current workflow is unchanged.
2. User explicitly enables local personal mode.
3. The site verifies local API health and the personal bundle identity.
4. The physician enters/selects patient context and diagnosis.
5. Engine returns source-traced owner-reviewed candidate regimens.
6. The site displays candidates and alternatives before applying anything.
7. The physician manually selects one candidate.
8. Only then is the structured regimen handed to the existing calculator
   functions for dose/formulation rendering.
9. The UI displays Engine trace, source, governance status, safety warnings,
   input completeness, and calculation steps beside the existing result.

If the API is unavailable or returns a blocked state, the normal standalone
calculator continues to work exactly as before. No hidden fallback to an
Engine recommendation is allowed.

## 9. Clinical safety behaviour

Personal mode preserves every existing hard-safety stage and adds no bypass.

It must block recommendation output when required inputs for the candidate are
missing, including weight for weight-based dosing or required renal/pregnancy
context. It must not infer unknown renal function, age group, formulation
concentration, or dose basis.

Ranges remain ranges. The system may calculate both boundaries but must not
choose a point inside a range without an explicit source rule and physician
selection. Maximum dose is applied visibly and recorded in trace.

Every output must allow the physician to answer:

1. Which guideline produced it?
2. Which regimens were considered?
3. Which safety filters changed or blocked it?
4. Which terminology mappings affected it?
5. Which Engine stages participated?
6. Why were alternatives rejected?
7. Which evidence supports the final displayed calculation?

## 10. Security and privacy

- Bind only to `127.0.0.1` by default.
- Reject non-loopback Host/Origin unless a future security RFC authorizes it.
- Do not store patient names, identifiers, contacts, or credential documents.
- Default request audit stores only minimized clinical inputs, hashes, mode,
  versions, result IDs, and safety/trace decisions.
- Registry, request audit, and personal bundles remain gitignored local data.
- No telemetry or cloud transmission in this RFC.

## 11. Implementation phases

### Phase A — governance acceptance

- Accept or reject this RFC explicitly.
- Amend `GOVERNANCE_SOURCE_OF_TRUTH.md` and the governance constitution only
  after acceptance.
- Define physician-owner registration and attestation policy.

### Phase B — contracts and guard

- Add mode enum/config without changing current defaults.
- Add personal bundle schema and validator.
- Add `PersonalPhysicianGuard` outside the frozen kernel.
- Add negative tests before any positive path.

### Phase C — owner curation workflow

- Register the real physician-owner locally.
- Present exact source/provenance review packets.
- Record append-only owner attestations.
- Build a small immutable owner-reviewed bundle; no bulk auto-approval.

### Phase D — API v2

- Add versioned full recommendation DTO and trace DTO.
- Keep API v1 behaviour and tests unchanged.
- Prove blocked/empty output for missing guard, source, inputs, or attestation.

### Phase E — calculator bridge

- Add explicit personal-mode control.
- Reuse existing calculation and formulation functions.
- Add candidate selection, trace/source panel, and persistent mode banner.
- Preserve offline/default behaviour when the API is absent.

### Phase F — acceptance

- Full canonical tests and clean-clone reproducibility.
- Arithmetic Golden tests for dose, range, cap, frequency, concentration, and
  formulation calculations.
- Owner-reviewed clinical Golden cases for the activated subset.
- Browser tests for default-mode equality and fail-closed personal mode.
- Security tests for loopback binding and no production-bundle contamination.
- Explicit owner acceptance before activation.

## 12. Required test matrix

At minimum:

- default calculator regression equality;
- API v1 regression equality;
- production profile still rejects uncurated data;
- research/development profiles cannot masquerade as personal mode;
- no/invalid owner registration -> blocked;
- invalid/stale/hash-mismatched bundle -> blocked;
- unreviewed regimen -> blocked;
- missing source wording/page/hash -> blocked;
- missing required patient input -> blocked;
- daily versus per-administration dose semantics preserved;
- ranges and footnote markers parsed without numeric concatenation;
- maximum-dose cap visible in result and trace;
- combination-component basis preserved;
- suspension/concentration arithmetic equals current calculator;
- allergy, renal, pregnancy, pediatric, neonatal, interaction filters preserved;
- API unavailable -> existing calculator still usable;
- no recommendation silently becomes `APPROVED`;
- personal bundle cannot enter production export.

## 13. Explicitly out of scope

- public deployment;
- replacing physician judgement;
- autonomous diagnosis or prescribing;
- weakening the two-reviewer production workflow;
- automatic conversion of C7 events into clinical approval;
- editing the production Review Workbench DB in place;
- changing frozen medical calculation logic during this RFC;
- mobile/cloud synchronization or multi-user authentication.

## 14. Acceptance criteria for this RFC

The RFC may be accepted only if the owner agrees that:

1. normal application behaviour remains the default and is regression-tested;
2. personal mode is explicit, local-only, traceable, and fail-closed;
3. owner-reviewed content is not labelled independently approved;
4. production governance remains unchanged;
5. implementation proceeds phase-by-phase with no direct Engine connection to
   unreviewed data;
6. the first activated dataset is a small manually reviewed subset, not the
   entire extracted corpus.

# RC-030 C5 — Architecture Audit and Hardening Findings

## Consolidation decision (Phase 16)

Two builder/template pairs existed: the main 60-record interface (non-blind — showed parser output before submission) and the 30-record control-sample interface (correctly blind, with a working post-submit reveal panel and AI comparison). Rather than fixing the main template independently and keeping two divergent implementations, the control-sample template's already-correct blind-then-reveal pattern was adopted as the **single** consolidated template, parameterized by a build-time `--mode {all,control}` flag. The two dataset shapes differ (the 30-record set carries `ai_proposed_verdict`/`ai_confidence`/`ai_evidence_explanation`/`ai_risk_flags`; the 60-record set does not), so the reveal panel degrades gracefully: it shows the full AI comparison when those fields are present and a plain "no AI proposal available" note otherwise. This satisfies "no duplicate implementation" without requiring new AI-review data to be generated for the 60-record set (out of scope for C5, which is interface-only).

## Findings (real defects found while auditing, not assumed)

| # | Finding | Severity | Fix |
|---|---|---|---|
| 1 | The main `owner_review_template.html` rendered `f_semtype` (parser candidate), `f_risk` (risk flags), `f_valstatus` (validation status), `f_eligibility` (calculation eligibility), and `f_rulefrag` (parser rule fragment) **before** verdict submission — a direct violation of the required blinding boundary (Part IV). | **Critical — blind-review violation** | Adopted the reveal-panel pattern (Phase 16 above); none of these fields render until `hasEvent` is true for the current record. |
| 2 | `owner_review_data.json` embedded `pdf_local_path: "C:/clinrec_downloader/downloads_active/<filename>.pdf"` in **every one of 60 records** — a machine-specific absolute path, explicitly forbidden by Phase 10 ("Do not embed: personal absolute paths; machine-specific roots; file URLs containing owner machine paths"). Found live in the browser during verification, not by static inspection alone. | **Critical — path-safety violation** | Removed `pdf_local_path` from both datasets. The template now resolves PDFs via an owner-configured local root (`prompt()`, stored only in `localStorage` under `rc030_owner_review_c5_pdf_root_v1`, never written to any file) combined with the dataset's bare `source_pdf` filename. The builder now hard-refuses (`_FORBIDDEN_DATA_KEYS`, `_ABS_PATH_RE`) any dataset record containing `pdf_local_path` or any string field matching an absolute-path shape, so this class of leak cannot silently recur. |
| 3 | The pre-submission per-record badge (added during initial C5 drafting, then caught in the same verification pass) displayed `r.workload_category \|\| r.stratum`. For 50/60 records, `stratum` is identical to `parser_semantic_type` (it is literally the sampling stratum key derived from the parser's own classification) — displaying it would have re-introduced the blinding violation from finding #1 through a different field. | **Critical — blind-review violation (self-introduced, caught before commit)** | `r.stratum` removed from the pre-submission badge entirely; only `workload_category` (a review-ordering label, not a parser output) is shown. Regression test added (`test_stratum_field_not_rendered_before_submission`). |
| 4 | Neither original template validated `test_event`'s type strictly in the in-browser import validator, and neither guarded against duplicate `event_id`/self-supersession on import. | Medium — defense-in-depth gap | The consolidated `validateImport()` now checks `typeof ev.test_event !== "boolean"`, rejects AI-provenance fields (`review_origin`/`owner_verified`/`clinically_approved`/`human_validated`), rejects duplicate `event_id` within an export, and rejects `supersedes_event_id === event_id`. |
| 5 | No note-length limit or control-character check existed in either template. | Low — hardening | `MAX_NOTE_LENGTH = 2000` (`maxlength` attribute + live char counter + submit-time check) and a control-character regex reject on submit. |
| 6 | Corrupt `localStorage` (unparseable JSON) was silently swallowed into an empty array (`catch(e) { return []; }`) in both original templates — this could let a corrupted store look identical to a fresh one, risking silent data loss on the next write. | Medium — fail-open on corruption | `loadStore()` now surfaces a blocking `alert()` and re-throws on parse failure instead of silently returning `[]`; nothing further executes on a corrupt store. |
| 7 | No explicit reset/clear control existed; there was no way to test the "no automatic destructive reset" requirement because there was no reset at all. | Low — missing required feature | Added a `Reset local store` button gated behind a `confirm()` dialog that states the event count and warns to export first; never runs automatically. |
| 8 | The submit button was always enabled/clickable even with no verdict selected (relying solely on an `alert()` after the click). | Low — UX/robustness | Submit button is now `disabled` until a verdict is selected (`updateSubmitEnabled()`), in addition to keeping the post-click validation as defense-in-depth. |
| 9 | Storage keys (`rc030_owner_fidelity_dryrun_v1`, `rc030_owner_control_sample_v1`) were not mode-parameterized in a single template, which would have collided if both modes were ever served from the same consolidated file without care. | Low — consolidation risk | New keys are template-literal mode-suffixed: `` `rc030_owner_review_c5_events_v1_${MODE}` `` / `` `rc030_owner_review_c5_session_v1_${MODE}` ``, with `MODE` fixed at build time (`--mode`), never user-editable. Verified distinct in a live browser session (main-mode store unaffected by a control-mode submission). |
| 10 | One `.innerHTML =` assignment (control-sample template's `badgeCurrent.innerHTML = ...${r.workload_category}...`) built markup via string concatenation from dataset content. Not exploitable with the current dataset's controlled vocabulary, but not the recommended pattern for untrusted-shaped text per Phase 14. | Low — content-security hardening | Rewritten using `createElement`/`textContent` (`badgeCurrent.appendChild(tag)`), consistent with the rest of the file's DOM-construction style. Regression test added (`test_template_uses_textcontent_not_innerhtml_for_record_data`). |

## Verified properties (live browser testing, not just static inspection)

- **Zero network requests** across the full test session (page loads to the local static server only; `read_network_requests` showed no other traffic before or after verdict submission).
- **No preselection**: `verdictSelect.value === ""` on every record render; submit button disabled until a value is chosen.
- **Blinding confirmed via `document.body.innerText`**: no parser semantic type, risk flags, validation status, or eligibility value appears in visible text before submission (only the generic disclaimer prose mentions the term `calculation_eligibility`, not a per-record value).
- **Whitespace-only note rejected** (`alert` fired, store unchanged); **real note accepted** (event recorded).
- **Submitted event schema validated against the actual committed C4 Python validator** (`dose_verification_sandbox.owner_fidelity_events.validate_event`) — zero issues, confirming end-to-end schema compatibility, not just visual similarity.
- **Storage isolation confirmed**: submitting in control mode did not create or touch the `..._all` storage key.
- **Deterministic build confirmed**: two independent builds from the same dataset are byte-identical (`diff` clean); `--check` mode correctly passes against a matching build and fails against a missing one.
- All browser-created test events were deleted from `localStorage` after verification (`localStorage.removeItem`/`clear()`), per the "do not create genuine owner events during tests" requirement — the events used `test_event: false` (matching real submission behavior, which is what needed verifying) but existed only in an ephemeral automated-browser session, never persisted to disk or git, and were explicitly cleared immediately after each check.

## Deferred (explicitly, not silently)

- **Table evidence display** (Phase 11 — clipped table image/embedded-text context, TABLE CONTEXT badge wiring to `clipped_table_recovery.json`): the badge CSS/logic exists (`table-badge`, keyed off `r.table_context`) but no dataset currently sets that field, and `clipped_table_recovery.json` (3 records) was not wired in — would need dataset-schema work beyond interface hardening. Documented, not implemented.
- **AI comparison for the full 60-record set**: requires running AI pre-review/audit over the 60-record set to populate `ai_proposed_verdict` etc., which is data-generation work outside C5's interface-only scope (and outside this session's authorization, which excludes AI event/dataset creation). The template already supports it (graceful degradation) — only the data is missing.
- **CLI export validator command** (Phase 9's suggested `python -m dose_verification_sandbox.validate_owner_export <file>`): the committed C4 `validate_events`/`filter_real_events` functions already serve this purpose when called from a short script or the REPL; a dedicated CLI wrapper was judged to add surface area without a proven need beyond what the in-browser `validateImport()` and the C4 Python functions already cover together. Deferred — flagged for a future turn if the owner wants a one-command CLI.
- **Full supersession-DAG resolution** for concurrent terminal events: same deferral as C4 (architectural design decision, not a bug fix).

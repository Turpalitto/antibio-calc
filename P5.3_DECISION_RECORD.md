# P5.3_DECISION_RECORD.md
## Architecture Decision Record — Regimen Assembly Source · 2026-07-15
## Status: ACCEPTED (owner decision, recorded before implementation)

## Context
P5.3 Phase 0 audit (`P5.3_IMPLEMENTATION_AUDIT.md`) proved that kb_p44 atomic Knowledge Objects
cannot be deterministically assembled into explainable clinical regimens: the `relationships` column
is empty on 100% of objects, and objects cluster only by `(guideline_id, page)` (e.g. 2 drugs + 52
unlinked doses on one page), so there is no data recording which dose belongs to which drug. This is
registered as **RC-023** (`ROOT_CAUSE_REGISTER.md`). The success criterion — "каждый regimen должен
быть объясним до конкретной строки клинической рекомендации" — cannot be met by combining unlinked
atomic facts.

## Decision
**The Regimen Assembly Layer uses `normalized_regimens` as the authoritative backbone of clinical
regimen candidates, and enriches those validated regimens with kb_p44 Knowledge Objects ONLY where
the provenance linkage is deterministic.** (Owner decision, 2026-07-15.)

Concretely:
1. **Preserve `normalized_regimens` as the source of regimen candidates.** Each row is already a
   complete, validated regimen (drug+dose+route+frequency+duration correctly associated by the
   original LLM extraction) with `source_pdf`/`source_page`/`source_quote` for line-level
   explainability. Not modified, not deleted, not re-derived.
2. **Enrich only on deterministic provenance linkage.** kb_p44 `Evidence` and `Contraindication`
   objects are attached to a regimen ONLY through an unambiguous shared key (`guideline_id`). No
   fuzzy/heuristic association.
3. **Never infer relationships.** If a candidate enrichment cannot be linked deterministically, it is
   not attached — the field is left `UNKNOWN` and the regimen flagged `NEEDS_REVIEW`, never guessed.
4. **Every added field carries provenance.** Any enrichment field records `source_object_id`,
   `source_document`, `source_location` (the kb_p44 object it came from), exactly like the base
   fields carry their `normalized_regimens` provenance.
5. **Missing linkage = UNKNOWN / NEEDS_REVIEW.** Absence is explicit and surfaced, never a silent
   default (the RC-012/RC-001 discipline, applied to enrichment).
6. **Metrics emitted every run:** `enriched_regimens_count`, `enrichment_coverage`,
   `unresolved_links`, `conflicts_found`.

## Why this option (over the alternatives)
- **Over "assemble from atomic kb_p44 objects" (literal Phase 2):** that path produces
  combinatorially-guessed drug↔dose pairings (RC-023) — deterministic but deterministically wrong,
  and unexplainable. Rejected on clinical-safety grounds.
- **Over "fix RC-023 first (extraction-layer linkage) then assemble atomically":** correct
  long-term, but a large extraction-layer architecture change that blocks all P5.3 progress. Deferred
  to a future cycle; not required to deliver a safe, explainable v1.

This decision keeps kb_p44's provenance contract as the canonical enrichment discipline (P5.0
`SINGLE_SOURCE_OF_TRUTH_RFC.md`) while sourcing regimen *structure* from the only store that has it
correctly today. The atomic-fact assembly path becomes viable later, once RC-023 is resolved, without
reworking this layer — enrichment simply gains more deterministic links.

## Consequences
- **Positive:** every assembled regimen is explainable to a specific `source_quote` line; no inferred
  associations; kb_p44 adds Evidence/Contraindication the engine input lacks today; nothing existing
  is modified (engine, frozen data, normalized_regimens all untouched).
- **Negative / limits:** enrichment is guideline-scoped (an Evidence/Contraindication linked by
  `guideline_id` applies to the guideline, and is attached to that guideline's regimens with
  guideline-level — not regimen-specific — provenance; this is stated, not hidden, on each enriched
  field). Regimen-specific enrichment awaits finer linkage (RC-023). Coverage of enrichment will be
  partial and is measured (`enrichment_coverage`), not assumed.

## Scope guardrails (STRICT RULES, restated)
Frozen medical data unchanged · `normalized_regimens.sqlite` preserved · Clinical Engine not switched
(shadow validation only) · all P5.3 code additive in a new `clinical_engine/regimen/` package + a new
`assembled_regimens.sqlite` · any new defect → Root Cause entry, not an immediate fix.

## 3. TherapeuticOption model (Task 2)
Independent dataclass (not a `ClinicalRegimen` subtype): `option_id, version, status, indication,
therapeutic_class, alternatives, selection_conditions, contraindications, source, source_page,
source_quote, guideline_id, field_provenance, lifecycle_state, review_status, approved_by,
approved_at, origin_regimen_id, origin_category`. **Verified by test** that it structurally has NO
`dose`/`route`/`frequency` fields at all — the separation is enforced by the type system, not by
convention.

## 4. Rules (Task 3)
`THERAPEUTIC_OPTION_RULES.md`: the one dividing rule is specific-drug+specific-dose (`ClinicalRegimen`)
vs. class/alternatives-without-dose (`TherapeuticOption`). A `TherapeuticOption` never gains a dose
field even for one alternative; never serves as a direct engine input (frozen `RecommendationCandidate`
contract unchanged); never silently absorbs a category-C (dose-present-somewhere) candidate.

## 5. Migration strategy (Task 4)
REJECT → `TherapeuticOption` only for category A/B **AND** `has_complete_provenance()` (source,
source_page, source_quote, guideline_id all present). On the real corpus: **652/652 migratable
candidates had complete provenance — 0 blocked.** Category C (457→444 after P5.4's route-recovery
already fixed 13) and D (23) remain unmigrated `ClinicalRegimen` candidates, correctly still REJECT.

## 6. Tests (Task 5)
10 new tests, **33 passed total** (14 P5.3 + 9 P5.4 + 10 P5.5): classifier correctness per category,
class recommendation migrates to `TherapeuticOption`, missing dose NEVER produces a fabricated
`ClinicalRegimen` (verified structurally — the type has no dose field to fabricate into), specific-
regimen-missing-extraction candidates stay `ClinicalRegimen` (not mis-promoted), provenance-gate
enforcement, exhaustive partition, and a real-corpus run asserting the exact verified counts
(627/25/457/23) as a regression guard against re-inflating any category.

## 8. Final question — can we proceed to P6?

**Yes, engineering-wise, with the same physician-capacity gate as before — and the corpus is now
substantially more usable than P5.4's numbers suggested.** After type separation:
- **1,556 ClinicalRegimen candidates** (569 PASS + 987 REVIEW) on a path to `PHYSICIAN_APPROVED`.
- **652 TherapeuticOption candidates**, also on the same review lifecycle (P5.2 governance, reused),
  representing real, previously-invisible clinical knowledge (drug classes, alternatives) now
  correctly modeled and explainable.
- **Only 467 (17.5%)** remain genuinely unresolved: 444 are real extraction gaps (route/dose text
  present but unparsed — deferred, extraction-layer, out of scope) and 23 are TB-specific table
  noise (RC-026, deferred).

**Remaining blockers to P6 (revised):**
1. Populate the review/approval workflow for BOTH `ClinicalRegimen` and `TherapeuticOption` — still
   physician-capacity-bound, not engineering.
2. Decide whether/how the Clinical Decision Engine should eventually consume `TherapeuticOption`
   knowledge (currently explicitly out of scope — reference-only) — a governance decision for a
   future milestone, not a P5.5/P6 blocker per se, since P6 can proceed serving `ClinicalRegimen`
   candidates alone while `TherapeuticOption` knowledge accumulates for later engine integration.
3. RC-023 (kb_p44 atomic linkage) and RC-025/RC-026 (data-quality/TB-extraction) remain open,
   deferred, tracked — none block P6's core path.

**The architectural question that motivated P5.5 (RC-024) is resolved**: REJECT is no longer a
single undifferentiated bucket hiding a modeling gap; it is now three honestly distinct outcomes
(genuine regimen defect, class-level knowledge, TB-specific noise), each correctly typed and each on
its own governed path.
